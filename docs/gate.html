The gate

One check, three places

The gate decides if a description follows the convention. The same code runs as a Claude Code hook, as a GitHub Action, and from the command line. A failure says what is wrong and how to fix it.

Where it runs

WhereWhenHow
Claude Code hookBefore gh pr create|edit, az repos pr create|update and the GitHub and Azure DevOps MCP create or update PR toolsDenies the call and lists the findings. Run /pr-brief to fix them.
GitHub ActionWhen a PR is opened, edited, pushed to, reopened or marked readyFails the check with one annotation for each finding. Reads the description from the event payload.
Command lineWhenever you run itpr-brief gate --file body.md. Exit 0 passes, 1 means findings, 2 means a usage or config error.

What it checks

  • The begin and end markers are both present, in order, and name a style and a theme.
  • The three parts exist, in order. The Brief is one paragraph of at most 5 sentences.
  • Every diagram is graph LR with the Input, Functions and Output boxes, inside the limits, with Input and Output nodes labelled only I1, O1, and so on.
  • Every id has a References row, and no row is unused. An id means one thing in the whole description.
  • The diagram style equals what the theme requires, including the invisible layout links.
  • The Read-these-first table has 1 to 7 rows.
  • The prose has no hard ASD-STE100 violations, unless the style is iceberg.
  • The description is at most 65,536 characters.

A real finding:

FAIL [style] diagram 1: the style does not match theme github-dark at style line 3.
      expected: classDef added fill:#12221d,stroke:#3fb950,stroke-width:1px,color:#e6edf3,font-weight:500
      found:    classDef added fill:#12221d,stroke:#3fb951,stroke-width:1px,color:#e6edf3,font-weight:500
      Run `pr-brief diagram` and paste its output.

The hook

The hook receives the tool call as JSON before Claude Code runs it. For a Bash call it looks for gh pr create|edit and az repos pr create|update, then reads the description from --body, --body-file, --description, a $(cat <<&#39;EOF&#39; ... EOF) heredoc, or $(cat file). For the MCP tools it reads the body or description field.

  • It never runs the text it reads. It only matches patterns, and it reads only files the command itself names.
  • It cannot read a shell variable or standard input. It denies the call and says to write the description to a file and use --body-file.
  • It makes no network calls, keeps no log and sends nothing.
  • A broken payload never blocks a call. The hook allows it and says why on standard error.
  • It adds about 16 ms to a Bash call.

In CI

Use the workflow from the home page, or run pr-brief init --workflow. Three details matter:

  • Check out the base commit. On a pull request event the default checkout is the merge commit, which contains the PR’s own .pr-brief.json. A PR could then loosen its own check. The base commit is safe because the gate reads only the config and the event payload, and never runs code from the PR.
  • Drafts and bots are skipped. Mark a PR ready, and the check runs.
  • No personal access token. The job needs only contents: read.

Annotations escape %, carriage returns and line feeds, so text in a description cannot end a workflow command or start another. The failing job also writes a summary that points at /pr-brief improve.

Skipping one PR

Some PRs should not carry a brief: a release PR, an automated bump. Put one visible line in the description:

> pr-brief skipped: release PR, notes are in the changelog

The reason is required and stays readable to reviewers. The gate still checks the length.

What it does not protect against

The gate is a quality control, not a security boundary. Anyone can edit a description in the web UI, call the REST API with gh api, or use the skip line. The gate keeps honest contributors consistent; it does not stop a determined one.

The threat model, including how the hook handles hostile input, is in SECURITY.md.
